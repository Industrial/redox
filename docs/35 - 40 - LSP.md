## 1. What this plan is

`redox-lsp`: a language server over `lsp-server` and `lsp-types`, per doc 02 §5.5. Four
capabilities, each one wired to something that already exists:

| Capability | What it calls |
|---|---|
| Diagnostics on change | `redox_driver::diagnose`, `redox_driver::lint`, and plan 07's rustc remap |
| Semantic tokens | `redox_lexer::lex` |
| Document symbols | `redox_ast::Program`'s items |
| Formatting | `redox_fmt::format` |

**The server contributes no analysis of its own.** That is the whole shape of the row, and it
is why doc 04's cell says Redox's is simpler than Emerald's 545 lines: there is no symbol
table to build, because document symbols are the item list, and no diagnostic engine to write,
because `Diagnostic` already carries a code, a severity, a span and a message.

### 1.1 Verified preconditions

Measured, not assumed.

**The crates exist and resolve.** `cargo search`, 2026-11-09:

```
lsp-server = "0.10.0"              # Generic LSP server scaffold.
lsp-types = "0.97.0"               # Types for interaction with a language server …
```

**Every input the four capabilities need is already public.**

```
redox_driver::diagnose(path, source, failure) -> Vec<Diagnostic>
redox_driver::lint(path, source)              -> Vec<Diagnostic>
redox_lexer::lex(source)                      -> Result<Vec<Token>, …>
redox_parser::parse_source(source)            -> Result<Program, ParseFailure>
redox_fmt::format(&program, source)           -> String
```

and `redox_diag::Diagnostic` is `{ code, severity, message, span, help, path, source }` —
which maps onto `lsp_types::Diagnostic` field for field, with `Severity::is_fatal` picking
`ERROR` or `WARNING`.

**One input is not.** Plan 07's rustc remap is `crate::check_command::remap::remap` in
`redox-cli`, and it is `pub(crate)`. §1.2 is what to do about it.

### 1.2 The remap has to move, for the reason the precedence table did

Doc 04's row 40 says *"rustc errors arrive already remapped to the `.sdx` through plan 07, so
the server reports them against the file the user wrote"*. They do not arrive at all: the
remap lives inside the CLI's `check` command, which is where plan 07 needed it and the only
place that has ever wanted it.

The server is the second consumer, and plan 34 leaf 3 §10.13 recorded exactly this situation
one row earlier — the parser's precedence table was `pub(crate)` and correct until the
formatter needed it, and a *copy* would have drifted silently because both spellings compile.
The same argument applies with more force here: a remap that disagreed with `redox check`
would point an editor's squiggle at the wrong line, and nothing would fail.

So **leaf 1 moves the remap to `redox-driver`** and `check_command` calls it there. That is a
refactor with no behaviour change, which is why it is its own leaf and its own commit: if the
move breaks anything, `tests/ui/` says so before any LSP code exists.

### 1.3 What a formatter hook buys that `redox fmt` does not

Plan 34 shipped `redox fmt` and `--check`. The LSP hook is `textDocument/formatting`, which is
the same function behind format-on-save — and it is the capability most likely to be *used*,
because an editor calls it on every save without being asked.

That makes it the capability whose correctness matters most and the one that needs the least
code: `redox_fmt::format` over the whole document, returned as a single full-range `TextEdit`.
A full-range edit rather than a diff is deliberate — plan 34's properties guarantee the output
is canonical and meaning-preserving, and a minimal-diff algorithm would be new code with no
property behind it.

### 1.4 Semantic tokens are the lexer's output, renamed

`lsp-types` wants a flat delta-encoded array of `(line, start, length, type, modifiers)`.
`redox_lexer::lex` already gives a token stream with spans, and doc 02 §5.5 lists semantic
tokens because a tree-sitter grammar (row 41) is a separate, larger job that this row does not
wait for.

The mapping from `TokenKind` to a semantic token type is the only design in it, and it is a
table. The `Indent`, `Dedent` and `Newline` tokens produce no token at all, which is worth
stating because they have spans and a loop that trusted the span would emit zero-width tokens
an editor renders as nothing — or as a glitch, depending on the editor.

## 3. Concrete proof this plan targets

**An LSP session driven over a pipe, in-process.** `lsp-server` exposes a `Connection` with a
memory transport for exactly this, so the test is a real server: send `initialize`, then
`textDocument/didOpen` with a `.sdx` fixture, then assert on the `publishDiagnostics`
notification that comes back.

Four assertions, one per capability:

1. A file with a syntax error publishes a diagnostic whose range is the `.sdx` span and whose
   code is the `RDX` code — **not** a rustc code and not a `.xrs` line.
2. A file using `.unwrap ()` publishes `RDX1001` as a **warning**, and one with the
   `-- redox: allow unwrap` pragma publishes nothing. Plan 38 built both; this asserts they
   survive the trip through the protocol, where a severity is an integer and an off-by-one is
   invisible.
3. `textDocument/documentSymbol` on `examples/class.sdx` returns its items.
4. `textDocument/formatting` on a non-canonical file returns an edit, and on an example returns
   none — which is plan 34 §1.5's *"the corpus is the style guide"* asserted through the
   protocol.

**Plus one negative**: a file that does not parse must still answer `documentSymbol` and
`formatting` without crashing the server. An editor sends requests while the user is
mid-keystroke, so the half-written state is the normal state, and a server that panics on it
is useless in exactly the moment it is needed.

## 4. Leaves

Ordered so each is shippable alone.

### Leaf 1 — `leaf-move-the-remap`

`remap` moves from `redox-cli` to `redox-driver` and becomes public. No behaviour change;
`tests/ui/` is the check. §1.2 is the argument.

### Leaf 2 — `leaf-server-skeleton`

`crates/redox-lsp/`: the `Connection`, the initialise handshake, the document store, and a
main loop that answers `shutdown`. Plus the in-process test harness of §3, asserting the
handshake and nothing else — so the harness is working before any capability depends on it.

### Leaf 3 — `leaf-diagnostics`

`didOpen`/`didChange` publish `diagnose` and `lint` output. The rustc pass is **not** here:
§6 says why.

### Leaf 4 — `leaf-symbols-and-formatting`

`documentSymbol` from the item list, `formatting` from `redox_fmt::format`. Both are small and
both need the same "the document may not parse" handling, so they travel together.

### Leaf 5 — `leaf-semantic-tokens`

The `TokenKind` table, and the delta encoding.

## 5. Acceptance criteria

1. `initialize` advertises exactly the capabilities implemented, and no others. A server that
   advertises what it does not do is worse than one that advertises nothing, because the editor
   stops asking elsewhere.
2. A syntax error publishes a diagnostic at the `.sdx` span with its `RDX` code.
3. `RDX1001` publishes as a warning; the pragma suppresses it.
4. `documentSymbol` returns one symbol per item, with the item's own range.
5. `formatting` returns a full-range edit for a non-canonical document and no edit for a
   canonical one.
6. Semantic tokens cover every token the lexer produces except `Indent`, `Dedent` and
   `Newline`, and the encoding is delta-correct — asserted by decoding it back.
7. **A document that does not parse crashes nothing**, and every capability answers.
8. The server exits 0 on `shutdown`/`exit` and does not hang. A server that leaks a process per
   editor session is a bug users report as "my machine is slow".

## 6. Out of scope, and what it discloses

- **The rustc pass.** `redox check` shells out to rustc, which takes seconds; running it on
  every keystroke is wrong, and running it on save needs a cancellation and debounce design
  that is bigger than the rest of this row. Leaf 3 ships the Redox-side diagnostics, which are
  the ones that fire while typing. **The remap still moves in leaf 1**, because the move is
  the part that rots if deferred — and §1.2's drift argument does not wait for a consumer.
- **Completion, hover, go-to-definition.** All three need name resolution, and Redox has none:
  AGENTS.md's rule that every check rustc can make, rustc makes, means there is no symbol
  table to answer them from. Naming them here rather than in a capability list that quietly
  omits them.
- **Incremental sync.** Full-document sync, because the parser is fast and a full parse per
  keystroke is measured in microseconds. Row 44's benchmarks are where that stops being an
  assertion.
- **The editor clients.** Row 49's, which is why this row is editor-agnostic by construction.
- **A tree-sitter grammar.** Row 41's. Semantic tokens are the lexer's answer to the same
  question, and the two are independent.

## 8. Emerald reuse

`crates/emerald-lsp`, 545 lines, is the layout to follow — one module per capability, a
document store keyed by URI, and the main loop as a dispatch table.

**What is deliberately not taken** is its symbol table. Emerald's LSP builds one to answer
completion and hover, and plan 90's warning is to purge the `(`-assuming heuristics first:
Emerald's server guessed at call syntax in several places, which is precisely the class of
mistake juxtaposition makes unrecoverable. Redox answers neither request, so it needs neither
the table nor the heuristics.

## 9. Decision log

| # | Decision | Alternative rejected | Why |
|---|---|---|---|
| 1 | Move the remap to the driver in its own leaf | Copy it, or reach into the CLI | A copy drifts silently and would aim an editor's squiggle at the wrong line while still compiling — plan 34 §10.13's argument, one row later |
| 2 | No rustc pass | Run `check` on save | Cancellation and debounce are a larger design than this whole row; the Redox-side diagnostics are the ones that fire while typing |
| 3 | A full-range `TextEdit` for formatting | A minimal diff | Plan 34's properties guarantee the whole output; a diff algorithm would be new code with no property behind it |
| 4 | No completion, hover or definition | Build a symbol table | Redox has no name resolution by design (AGENTS.md), so each would be a guess |
| 5 | Full-document sync | Incremental | The parser is fast enough that incremental sync is a complication without a measurement; row 44 is where that claim gets tested |
| 6 | Test over an in-process `Connection` | Spawn the binary and speak JSON-RPC over pipes | The same protocol path with no process management, so a hanging test is a deadlock in the code and not in the harness |
| 7 | Advertise only what is implemented | Advertise optimistically | An editor that is told a capability exists stops looking for another source for it |
